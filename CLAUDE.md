# Маргиналии

Веб-инструмент вычитки Markdown: документ показывается с номерами физических
строк, замечания привязаны к строкам, рецензия выгружается одним `.md`-файлом.
Текст статьи не покидает браузер читателя — ни при открытии, ни при выгрузке.
Это свойство продукта, а не деталь: правка, добавляющая сетевой запрос с
содержимым документа, ломает его назначение.

## Команды

```sh
pnpm install
pnpm run dev            # разработка, Vite
pnpm run test:setup     # разово: Chromium для Playwright
pnpm test               # обязательный контур целиком
pnpm run deploy         # ручная выкладка; обычно достаточно push в main
```

`pnpm test` = модульные проверки → сборка → заголовки → браузерные сценарии →
замеры отклика. Порядок не случаен: `test:headers` и `test:e2e` работают по
собранной сборке, поэтому `build` идёт до них. Отдельный набор запускается через
`pnpm run test:unit | test:headers | test:e2e | test:perf`.

Пакетный менеджер — pnpm 11.8.0. `npm` и `yarn` в этом репозитории не
используются.

## Порядок работы

Правка → `pnpm test` целиком → коммит. Ослаблять проверку, поднимать порог или
исключать набор ради зелёного прогона нельзя: пороги здесь получены измерением,
а не выбраны из удобства.

Сообщения коммитов — по-английски, в форме Conventional Commits
(`feat:`, `fix:`, `perf:`, `test:`), тело по существу, перенос около 80 знаков.
Комментарии в коде и тексты интерфейса — по-русски.

Публикация происходит сама: push в `main` запускает
`.github/workflows/deploy.yml`, который прогоняет `pnpm test` и выкладывает
`dist` на Firebase Hosting (проект `my-nikita-tools`, сайт `marginalia-review`).
Красный прогон не выкладывается.

## Комментарии

Комментарий объясняет причину, а не пересказывает код. Если из строки видно
«что», комментарий нужен только там, где неочевидно «почему»: почему выбран
именно этот механизм, чем плох очевидный, какой случай он закрывает. Комментарии
в этом репозитории написаны так — держитесь той же меры.

## Что легко сломать

**Файл рецензии — недоверенный вход.** Рецензию присылают письмом и открывают
чужим файлом. Машинные поля едут в HTML-комментарии `<!-- marginalia:1 … -->` и
разбираются `JSON.parse`, поэтому в них может лежать что угодно. Любая запись —
и из файла, и из IndexedDB — проходит `normalizeEntry` в `src/core.js`, который
пересобирает её по известной форме. Добавляете поле записи — добавьте его туда
же, иначе оно попадёт в разметку как есть.

**Карточки рецензии собираются строкой.** `renderReview` в `src/app.js` строит
разметку конкатенацией ради скорости на длинной рецензии. Значит ни одно
значение не попадает в неё без `escapeHtml` — включая те, что по замыслу
содержат число или элемент известного набора. Проверка на это есть в
`tests/e2e`, и она краснеет на неэкранированном поле.

**Что видно на экране, то и уедет в файл.** Цитата замечания и указатель поиска
строятся из готового DOM: `indexFragment` складывает `span.textContent`,
`wholeLineSelection` берёт цитату оттуда же, `createAnchoredEntry` — из
`selection.toString()`. Значит любая правка, меняющая **отображаемый** текст,
немедленно попадает в рецензию и в поиск, хотя правили вы показ. Так вышло с
неразрывными пробелами: без обратного перевода они уехали бы в выгружаемый
`.md` и перестали бы находиться поиском по обычному пробелу. Меняете показ —
проводите значение через `asTyped` в `src/app.js` или заводите такой же
обратный перевод рядом с ним.

**Иконки берутся из подмножества.** `src/fonts/material-symbols-rounded.woff2`
содержит ровно те девять глифов, что уже нужны интерфейсу. Имя иконки вне этого
набора не роняет сборку и не красит тесты — браузер печатает его словом прямо в
кнопке, и это уезжает в рабочий адрес. Нужен новый знак — либо нарисуйте его
инлайновым `svg` на классе `.glyph`, как сделано у кнопки вставки замечания,
либо пересоберите подмножество по `src/fonts/README.md`.

**У панели рецензии два режима.** Ниже 430 пикселей контейнерный запрос в
`src/styles.css` поджимает и строку действий, и список. Запросы для строки
действий объявлены **выше** базового правила `.review-list`, поэтому правило,
дописанное в тот же запрос, при равной специфичности проигрывает базовому по
порядку — молча и только на узкой панели. Сетку панели задаёт одна переменная
`--review-gap`; меняете её — меняйте там, а не в трёх местах. Браузерный
сценарий обязан мерить обе ширины: дефект, который был виден на панели в 310
пикселей, не виден ни на одной широкой.

**Хеш инлайнового скрипта.** В `index.html` есть инлайновый скрипт
перенаправления с зеркального адреса; строгая `Content-Security-Policy` в
`firebase.json` разрешает его по `sha256`-хешу. Правка этого скрипта без
пересчёта хеша молча ломает рабочий адрес. `pnpm run test:headers` считает хеш
из собранного файла и сверяет с политикой — не пропускайте этот набор.

**Заголовки безопасности не видны обычному прогону.** Браузерные сценарии идут
против сервера разработки, который о `firebase.json` не знает. Набор
`tests/headers` поднимает собственный сервер над `dist` с теми же заголовками —
он единственный, кто ловит политику, ломающую приложение.

**Отклик важнее красоты.** `tests/perf` меряет длинные задачи главного потока на
статье в 20 000 строк с замедлением процессора и блокирует сборку при
превышении. Пороги и причины записаны в комментариях `tests/perf/perf.spec.js`.
Документ собирается порциями с уступкой главному потоку; чтение геометрии в
цикле по строкам возвращает заморозку на десятки секунд — так уже было.

**Замер ломается молча.** Прежде чем мерить, набор ждёт готовности приложения по
конкретным узлам — счётчику строк в шапке и признаку завершённой сборки, — и
ждёт по десять минут каждый. Переименованный узел или разбитый на части текст
внутри него не красят прогон, а подвешивают его: сорок секунд превращаются в
двадцать минут. Правите шапку — загляните в `tests/perf/perf.spec.js` вместе с
ней.

**Замер меряет и машину тоже.** Множитель замедления калибруется от текущей
скорости процессора, поэтому открытый сервер предпросмотра, второй браузер или
параллельная сборка растягивают набор и портят числа. Перед `pnpm test` закройте
предпросмотр — иначе прогон покажет состояние стола, а не приложения.

**Номера строк.** `data-source-line` пишется прямо в разметку в
`src/markdown.js`, а сам номер рисуется через `::before` и держится за колонку
группы `.document-chunk`, а не за свою строку. Измерять отступы из JavaScript не
нужно — это и была причина той заморозки.

**Хранилище переживает обновление.** Документы и рецензии лежат в IndexedDB и
живут неделями. Изменение формы записи обязано учитывать уже сохранённое:
пользователь не переустанавливает приложение ради вашей правки.

**Обновление применяется само, но не под руками.** PWA собран с
`registerType: "prompt"`, и `keepAppFresh` в `src/updates.js` сам применяет
скачанную версию — но только когда вкладка скрыта и не открыт черновик или
форма правки. Человек уходит на старой версии, возвращается на новой, и
набранный текст никуда не девается. Условие безопасности задаёт приложение
(`state.draft`, `state.edit`), а не служба: она о наборе текста не знает.
Ослабите условие — вернёте перезагрузку посреди написанного замечания.

**Стили сверяются с макетом.** Исходный и собранный CSS напрямую несопоставимы,
поэтому осознанные расхождения перечислены в `design-sync-accepted.txt`. Запись,
переставшая соответствовать реальному расхождению, роняет сверку — список не
может пережить различие, которое описывает.

## Границы

Не меняйте без отдельного решения: формат файла рецензии (это публичный контракт
между версиями), адрес публикации, версии зависимостей, содержимое
`design-sync-accepted.txt`. `markdown-it` намеренно остаётся на 14.x: в 15.0
удалены внутренние подпути экспорта, а рендерер здесь подменён вручную.
